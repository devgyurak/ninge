# CP15, the ARM9 system control coprocessor (minimal)

Sources: GBATEK "ARM CP15 System Control Coprocessor" (Overview, ID Codes, Control Register,
Protection Unit, Cache Control, Tightly Coupled Memory, Misc); GBATEK "ARM Opcodes: Coprocessor
Instructions (MRC/MCR, LDC/STC, CDP, MCRR/MRRC)".
Used by: `crates/core/src/cpu/cp15.rs`, `crates/core/src/cpu/exception.rs`   Phase: 1 (#15)

Only the ARM9 has a CP15; the ARM7 has none (`arm-exceptions-modes.md`, "Coprocessor
instructions"). This note covers what the system needs in Phase 1: the control register (vector
base, TCM enable bits), the TCM region registers, and the read-only ID registers. The
protection-unit registers and the cache commands are accepted and held, but have no effect. The
bus that maps TCM into the address space is #18 (Phase 2, `memory-map.md`).

## Access

CP15 is reached by MCR (ARM to CP15) and MRC (CP15 to ARM) with coprocessor number 15:

| Bits | Field |
|---|---|
| 23-21 | opc1 (GBATEK's `<cpopc>`); 0 for every register below. Only the TCM and cache BIST registers at C15 use opc1 1 and 2 |
| 20 | 0 = MCR (write), 1 = MRC (read) |
| 19-16 | CRn |
| 15-12 | Rd |
| 7-5 | opc2 (GBATEK's `<cp>`) |
| 3-0 | CRm |

A register is named `CRn,CRm,opc2` below. CDP, LDC and STC cannot be used with CP15 (GBATEK);
what they do is in `arm-exceptions-modes.md`.

Rd = R15 has two GBATEK statements that do not agree. The CP15 overview says Rd can be R0-R14
and that R15 should not be used with CP15. The general coprocessor text says an MCR with R15
hands the coprocessor the value PC+12 (the instruction address + 12), and an MRC with R15 copies
bits 31-28 of the read value into CPSR bits 31-28 (N, Z, C, V), ignores the other bits, and
leaves R15 and CPSR bits 27-0 alone. The general rule is applied here; see "Unverified".

### C0,C0,0 / 1 / 2 — ID registers

On the DS ARM9: Main ID `41059461h` (ARM, ARMv5TE, ARM946, revision 1); cache type
`0F0D2112h` (separate caches, 8 KiB instruction and 4 KiB data, 32-byte lines); TCM size
`00140180h`. C0,C0,2 bits: 2 = ITCM absent, 6-9 = ITCM size (512 shl N), 14 = DTCM absent,
18-21 = DTCM size (512 shl N); `00140180h` is N = 6 for the ITCM (32 KiB) and N = 5 for the DTCM
(16 KiB), both present. Registers C0,C0,3..7 return the same value as C0,C0,0.

The other registers listed in GBATEK's table at CRn = 0 (the "ARM11" ones at CRm = 1 and 2) are
not part of the ARM9.

### C1,C0,0 — control register

| Bit | Meaning | On the ARM9 |
|---|---|---|
| 0 | MMU/PU enable | R/W |
| 1 | Alignment fault check | 0 |
| 2 | Data cache enable | R/W |
| 3-6 | Write buffer, 32-bit exceptions, 32-bit address faults, late abort | always 1 |
| 7 | Big-endian | R/W |
| 8-10 | System / ROM protection, implementation defined | 0 |
| 11 | Branch prediction | 0 |
| 12 | Instruction cache enable | R/W |
| 13 | Exception vectors: 0 = `00000000h`, 1 = `FFFF0000h` | R/W |
| 14 | Cache replacement: 0 = pseudo-random, 1 = round-robin | R/W |
| 15 | Pre-ARMv5 mode (LDM/LDR/POP to PC bit 0, Thumb) | R/W |
| 16 | DTCM enable | R/W |
| 17 | DTCM load mode (0 = R/W, 1 = write-only) | R/W |
| 18 | ITCM enable | R/W |
| 19 | ITCM load mode (0 = R/W, 1 = write-only) | R/W |
| 20-31 | reserved or not on this CPU | 0 |

GBATEK: bits 0, 2, 7 and 12-19 are read/write, bits 3-6 are always set, all others are zero.
A read therefore gives `(written & 000F_F085h) | 0000_0078h`.

Bit 13 is the exception vector base the ARM9 uses (`arm-exceptions-modes.md`, "Vector base").
In load mode a TCM that is enabled becomes write-only: loads read the underlying memory and
stores go to the TCM, so a program can copy into the TCM over the same addresses; it works for
every load and store instruction except SWP and SWPB (GBATEK, "TCM Enable, TCM Load Mode").

### C9,C1,0 / C9,C1,1 — TCM region registers

| Bits | Meaning |
|---|---|
| 0 | reserved, 0 |
| 1-5 | virtual size N: size = 512 shl N; N = 3 (4 KiB) to N = 23 (4 GiB) |
| 6-11 | reserved, 0 |
| 12-31 | region base, address = value shl 12; must be aligned to the size |

The virtual size normally equals the physical size from C0,C0,2, but may be smaller (only the
first part of the TCM is used) or larger (the area is filled with mirrors of the TCM). The ITCM
base is fixed: on the DS it is always `00000000h`, though the size can still be changed to mirror
the ITCM upward. If the DTCM and ITCM overlap, the ITCM has priority. The region is in effect
only while its enable bit in C1,C0,0 is set (bit 16 DTCM, bit 18 ITCM).

The resolved view of a TCM is its base, size in bytes, enable bit and load-mode bit.

### C2, C3, C5, C6 — protection unit

GBATEK describes the eight protection regions, their permissions and cachability, and that
region 7 wins over lower regions where they overlap. They are held and read back; **no access is
checked against them**, so the protection unit never raises an abort here
(`TODO(phase8)`, the accuracy phase).

| Register | Bits held |
|---|---|
| C2,C0,0 / 1 and C3,C0,0 | 0-7 (a bit per region); 8-31 reserved, 0 |
| C5,C0,0 / 1 | 0-15 (two bits per region); 16-31 reserved, 0 |
| C5,C0,2 / 3 | 0-31 (four bits per region) |
| C6,Cm,x | 0 enable, 1-5 size, 12-31 base; 6-11 reserved, 0 |

The region registers are unified on the DS: C6,Cm,1 reads and writes the same storage as
C6,Cm,0. The cachability and permission registers are not unified (a data copy and an
instruction copy exist).

### C7 — cache commands and halt

C7 is write-only: CRm and opc2 select a command and Rd carries its operand. The ARM9 commands
are invalidate, clean, clean-and-invalidate, prefetch of an instruction cache line, and
wait-for-interrupt (C7,C0,4 and C7,C8,2). No cache is modeled, so every cache command is
accepted and does nothing. Wait-for-interrupt should halt the core until an interrupt is
pending; that is Phase 3 (`TODO(phase3)`), and for now it does nothing.

### C13 — process ID

The FCSE process ID (C13,C0,0) is read-only and always zero on the DS; a write is ignored. The
trace process ID is read/write with no pin-out, and C13,C1,1 mirrors C13,C0,1.

## Behavior

- A write goes to the register that CRn, CRm and opc2 select. A read returns it.
- The control register keeps only the writable bits and reads with bits 3-6 set.
- Reading and writing registers never changes memory or raises an exception here; TCM and
  protection state take effect only when a later phase consults them.

## Edge cases

- Writing a read-only register (C0, C13,C0,0) is ignored.
- A combination not in the table above (a different CRn, CRm or opc2, or a non-zero opc1) is an
  unmapped register: see "Unverified".
- MRC with Rd = R15 sets the flags from the read value and writes no register; MCR with Rd = R15
  sends PC+12 (the general rule, not confirmed for CP15: see "Unverified").
- Any mode may access CP15 here (see "Unverified").

## Not modeled

- **The built-in self-test (BIST) registers** at C15 (opc1 0, 1 and 2; GBATEK describes them as
  read/write diagnostics). They are treated as unmapped: a read returns 0 and a write is
  ignored. — `Cp15::read`, `Cp15::write` carry `TODO(phase8)`.

## Unverified

- **Power-on and reset values** of every writable register. GBATEK gives none. They start at zero
  (so the control register reads `00000078h`: low vectors, TCM and PU off), and a core reset
  leaves CP15 alone. — `Cp15::new` in `crates/core/src/cpu/cp15.rs`, `Cpu::reset` in
  `exception.rs` — verify by a test ROM on real hardware.
- **Rd = R15** (`Cpu::cp15_transfer`, `Cpu::write_transfer_target` in `exception.rs`): GBATEK's
  CP15 overview says R15 should not be used, while its general coprocessor text gives the PC+12
  and flag-load rules; applying the general rules to CP15 is a guess. — verify by a test ROM on
  real hardware.
- **Privilege:** MCR and MRC to CP15 run in every mode, User included. GBATEK does not say; the
  ARM architecture documents may restrict CP15 to privileged modes, with an Undefined exception
  otherwise, but that has not been checked against them. — `Cpu::coprocessor` in `exception.rs` —
  check the ARM946E-S TRM, then verify by a test ROM on real hardware.
- **Unmapped registers** (any CRn/CRm/opc2 not listed, and opc1 other than 0): the table says
  nothing. Here a read returns 0 and a write is ignored; it
  could instead be an Undefined exception. — `Cp15::read`, `Cp15::write` — verify by a test ROM
  on real hardware.
- **A read of the write-only C7** returns 0 here. — `Cp15::read` — verify likewise.
- **Writes to the ID registers** are ignored (GBATEK marks them read-only without saying more). —
  `Cp15::write` — verify likewise.
- **Reserved bits in the held registers** (C2, C3, C5, C6, C9 TCM): they are dropped on a write
  and read as zero, taking GBATEK's "reserved/zero" literally. — `Cp15::write` — verify
  likewise.
- **The relation between C5,C0,0 and C5,C0,2** (the two-bit and four-bit permission views):
  GBATEK lists them separately; they are separate storage here. — `Cp15` fields — verify
  likewise.
- **C9,C0,x lockdown registers:** GBATEK gives two formats and no access type or width for the
  DS; they hold the written 32-bit value here. — `Cp15` fields — verify likewise.
- **TCM region corner cases:** a size field N outside 3-23, and a base that is not aligned to
  the size, are held as written and reported as written (size = 512 shl N); what the hardware
  does is not stated. The ITCM base reads 0 whatever is written, from "always `00000000h`".
  — `Cp15::itcm`, `Cp15::dtcm` — verify likewise.
- **Effect of the control bits that are only held** (big-endian bit 7, pre-ARMv5 mode bit 15,
  cache enables 2 and 12, replacement bit 14): nothing consults them yet. — the control mask in
  `cp15.rs` — implementing them is a later phase.
- **MCR2 and MRC2** (condition field 1111) are stepped past and do not reach CP15; that is the
  state of the whole 1111 space (`armv5te.md`, "Unverified"). — `unconditional_kind` in
  `crates/core/src/cpu/decode/mod.rs`.
